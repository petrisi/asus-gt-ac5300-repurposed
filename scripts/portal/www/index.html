Entries in the netfilter connection-tracking table. Every active flow through the router takes one. Exhaustion makes new connections fail outright; normal home use stays in the hundreds, far below the 300,000 ceiling.
Blocked inbound

Packets that hit the router's own INPUT chain and matched a DROP rule — traffic aimed at the router, not through it. Most is ordinary broadcast and discovery noise from the upstream network. A sustained spike means something is probing the box.

ARP neighbours
Devices in the router's ARP cache — a rough count of what it has spoken to recently, not a live client list. It counts anything the router has exchanged traffic with, including its own upstream gateway, so it is never zero on a connected box.
NVRAM used
–%
ASUS keeps all configuration in a fixed-size NVRAM area. Filling it makes settings silently fail to save — a well-known failure mode on these routers. Worth watching if you add many rules, clients or port forwards.
USB storage
–%
Capacity of the USB volume mounted at /tmp/usb, holding Entware and the torrent data. Nothing on this page depends on it — if the stick is pulled the tile reads "not attached" and everything else carries on, because the collector checks the mount table before touching the path (calling df on a stale mount point can block indefinitely).

Per-core utilisation

CPU cores
nowpeak
Routers frequently peg a single core while the aggregate looks idle — one core handling a flow the hardware accelerator couldn't take. That's invisible in the CPU tile, which is why the split is shown separately.

The thin peak-hold tick on each bar marks the highest value that core reached in the last 60 seconds; the same figure appears in the peak column. Both numeric columns are fixed width, so nothing shifts when a peak appears or expires. Because samples arrive every 2 seconds, a spike can start and finish between glances — the tick keeps it visible after the bar has already dropped back. Its brightness is its age: a sharp, bright tick means the peak happened moments ago; a faint one means it is nearly a minute old and probably not what you are currently looking at. Once the peak ages out of the window, or the live value catches up to it, the tick disappears.

Per-station airtime

from wl bs_data — the same counters the band-steering daemon reads
Station Radio PHY Data Air use Retries
All of this comes from the closed-source Broadcom wl driver, which exposes a surprising amount read-only. Hover any column heading for a short version.
BandTri-band hardware: one 2.4 GHz radio and two independent 5 GHz radios, each with its own channel, airtime and clients. They are separate radios, not one band split in two.
StateWhether the radio is transmitting. Worth knowing that wl radio returns a disable mask — 0x0000 means ON, 0x0001 means off. Easy to read backwards.
ChannelPrimary channel and width — 60/80 is channel 60 at 80 MHz. Selected by acsd when the band is set to auto. On 5 GHz many channels are DFS, where the radio must monitor for radar and may move on its own.
NoiseMeasured noise floor in dBm; more negative is better. Around −90 is a clean band, −80 or above means a congested or electrically noisy environment. This is the floor your signal has to rise above, so it caps achievable range and speed regardless of transmit power.
BusyShare of airtime already in use, derived as 100 − idle from chanim_stats. Critically this includes other people's networks on the same channel — high busy with zero clients of your own is neighbouring traffic, not a fault here. Wi-Fi is half-duplex, so busy airtime directly reduces what your own clients can get.
GlitchesPHY-layer decode errors counted since the radio started. The number is cumulative, so a large total on a long-running radio is normal — rate of climb is the signal. Fast growth points at interference on that channel (often non-Wi-Fi sources) rather than at any client.
ClientsDevices currently associated with this radio, from assoclist. Once clients connect, per-device signal strength and rates become readable via sta_info.

Leases handed out by this router's own dnsmasq on its LAN subnet (–), read from /var/lib/misc/dnsmasq.leases. This list is empty until something connects to a LAN port or an enabled radio. When this router runs in wireless-router mode, clients leasing here sit behind its own NAT and firewall — isolated from whatever network its WAN port is plugged into. Blocked inbound counts packets aimed at the router itself; blocked forwarded counts traffic it refused to route onward — the latter is the interesting one once this box has clients behind it. Accelerated flows are connections the Broadcom Packet Flow Cache is handling in hardware; traffic terminating on the router is never accelerated, so it reads 0 until clients forward through. Rule counts are ASUS-generated — 100+ filter rules is normal, and the count jumping is a useful signal that something rewrote the firewall.

IPv4 vs IPv6. The kernel keeps these in separate files (/proc/net/sockstat and sockstat6), and the firewall keeps them in separate tables (iptables and ip6tables) — a rule on one has no effect on the other. Sockets in use counts listeners, half-open and time-wait sockets as well as live ones, so it always exceeds Established. The established split is the honest measure of how many peers are actually connected over each protocol, which on a dual-stack seed is the number worth watching: if the v6 share is zero while IPv6 is up, the v6 firewall is probably blocking the peer port.

Known hosts (ARP)

History is recorded with rrdtool into round-robin databases on the USB stick, sampled once a minute. Round-robin means fixed size forever: older data is consolidated rather than accumulated, so a year of history costs the same ~1.8 MB as the first day.

This layer is optional by design. The live dashboard above reads only status.json from RAM and has no dependency on the USB stick or Entware. Remove the stick and everything above keeps working; only this section goes away.

Gaps are real. A missing minute is stored as unknown, not as zero, and is drawn as a break in the line. If the collector stalls, you see a hole rather than a flat line that looks like a genuinely idle router — a distinction this box has needed more than once.

Resolution falls with age, which is how the fixed size is achieved: 1-minute detail for 24 hours, 5-minute for a week, 30-minute for a month, 6-hour for a year. A brief spike visible in the 24-hour view is averaged away in the yearly one — that is consolidation working, not data loss.

Transfer totals integrate the recorded rates over each window. Coverage states what fraction of that window actually holds data: a total spanning an outage under-reports, and coverage is how you tell.

BitTorrent is measured two ways, and neither is the whole story. The totals come from Transmission's own lifetime counters: authoritative for payload volume, but written to disk only every few minutes, so a rate derived from them is a row of spikes separated by zeroes rather than a line. The peer-port chart instead reads firewall byte counters, which advance continuously.

What the chart measures is traffic on port 51413, not transfers. Two effects pull in opposite directions. It over-counts because the DHT shares that port and never idles — measured at 27.7 kB/s of outbound UDP while Transmission reported zero upload. It also under-counts, because connections this router opens outward carry an ephemeral source port that no port-based rule can match; against Transmission's figures the inbound counters caught only ~53% of a download, which was dominated by outbound-initiated peers. Read it as "what BitTorrent is putting on the wire", and read the totals for how much was actually transferred.
